# 2026-08-19 사용량 표시 오류에서 얻은 인사이트

이번 작업에서는 두 가지 겉보기에 다른 증상을 추적했다.

- 한도 창이 리셋된 뒤 제목 옆 변화량이 `-68%p`처럼 표시됨
- Claude Code `/usage`는 `73/66/77%`인데 ccmeter는 `0/46/66%`를 표시함

둘 다 계산식 자체보다 **값이 속한 시간 범위와 값의 출처를 함께 다루지 않은 것**이
근본 원인이었다.

## 1. 누적값의 차이는 같은 한도 창 안에서만 계산한다

사용률은 단조 증가하는 것처럼 보이지만 한도 창이 리셋되면 높은 값에서 낮은 값으로
돌아간다. 앱 실행 후 첫 표본과 마지막 표본을 무조건 빼면 이 정상적인 리셋이 큰 음수
변화로 표시된다.

따라서 변화량과 차트는 모두 현재 `Window`의 시작 이상, 리셋 시각 미만인 표본만
사용해야 한다. 회귀 테스트도 단순한 양수 증가뿐 아니라 다음 경계를 포함해야 한다.

- 이전 창의 높은 표본
- 새 창의 첫 표본
- 새 창 안에서 증가한 두 번째 표본

## 2. 애플리케이션 소유가 아닌 캐시는 최신 상태를 보장하지 않는다

관찰 당시 Claude Code 캐시
`~/.claude/token-scope-oauth-usage.json`의 `captured_at`은 2일 전이었다. 반면 같은
시점의 `ccmeter --live`는 Claude Code `/usage`와 일치하는 값을 반환했다. 즉 로컬
파일을 읽을 수 있다는 사실과 그 파일이 계속 갱신된다는 보장은 별개다.

외부 애플리케이션의 캐시는 다음 원칙으로 다룬다.

- 파일 수정 시각이 아니라 응답 안의 `captured_at`으로 신선도를 판단한다.
- 화면에 출처, 기준 시각, 갱신 실패 여부를 함께 표시한다.
- 외부 캐시와 자체 캐시가 있으면 `captured_at`이 더 최신인 값을 선택한다.
- 외부 캐시의 갱신 정책에 핵심 동작을 의존하지 않는다.

## 3. 성공한 원격 조회는 다음 실패를 견딜 수 있게 보존한다

수정 전에는 직접 조회가 성공해도 그 응답을 화면에만 사용했다. 바로 다음 요청이
HTTP 429를 받으면 프로그램은 다시 2일 전 Claude Code 캐시로 폴백했다. 그래서
한 번 최신값을 보여준 뒤 오래된 값으로 되돌아가는 현상도 가능했다.

성공한 응답은 agentmeter 소유의
`~/.cache/agentmeter/claude-usage.json`에 원자적으로 저장한다. 이후 조회가 실패해도
마지막으로 확인된 최신값을 유지할 수 있다. 저장 실패는 성공한 조회 자체를 실패로
바꾸지 않되, 부분 파일을 읽지 않도록 임시 파일을 쓴 뒤 교체한다.

## 4. 폴링 주기와 원격 조회 주기는 분리한다

TUI는 화면과 남은 시간을 자주 갱신해야 하지만 `/api/oauth/usage`는 연속 호출 시
HTTP 429를 반환한다. 따라서 60초 UI 폴링이 매번 네트워크 요청을 뜻해서는 안 된다.

- 신선한 캐시는 네트워크 없이 재사용한다.
- 오래된 경우에만 직접 조회한다.
- 실패 후에는 파일 기반 백오프를 적용해 프로세스를 다시 실행해도 연속 호출하지 않는다.
- `--live`는 명시적인 진단·강제 조회 수단으로만 사용한다.

## 5. 재현은 표시값과 원본 출처를 같은 순간에 비교한다

이번 진단에서 가장 유효했던 비교는 다음 세 가지였다.

1. Claude Code `/usage`의 표시값
2. `ccmeter --json`의 `captured_at`, `source`, `stale`, 한도 값
3. `ccmeter --live --json`의 직접 조회값

기본 조회는 오래된 값을, 강제 조회는 Claude Code와 같은 값을 반환해 모델 매핑이나
프로모션 보정보다 캐시 선택 경로가 원인임을 빠르게 분리할 수 있었다. 수정 전에는
회귀 테스트를 먼저 추가해 자체 캐시 저장·복원 경로가 없다는 점을 실패로 고정했다.

## 설계 체크리스트

향후 다른 공급자의 사용량 소스를 추가할 때 다음을 확인한다.

- 값과 함께 측정 시각, 출처, 한도 창을 모델링했는가?
- 리셋 전후 표본을 같은 변화량 계산에 섞지 않는가?
- 성공한 원격 응답을 안전하게 보존하는가?
- 캐시가 낡았거나 갱신에 실패했음을 사용자가 알 수 있는가?
- UI 갱신 주기와 네트워크 호출 주기가 분리되어 있는가?
- 429, 오래된 외부 캐시, 창 리셋에 대한 회귀 테스트가 있는가?
